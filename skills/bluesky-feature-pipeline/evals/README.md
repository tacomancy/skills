# Evaluation fixtures

`evals.json` names the prompts, the fixture under `fixtures/` each runs against, and what to check. The fixtures are one feature — reading goals in `acme/reader`, a reading tracker — at every stage of the pipeline, written out so a run can be read against them without a live repository: the adopting repository's guidance file with a post-merge section whose triggers fire on issue events as well as diffs, and the same file as it stood before stage 1 wrote the tiers; two skill inventories, one with every example skill installed and one with the pipeline alone; the repository before stage 0, with its own PR template and tickets in flight; the brief with its empty Changelog; the pinned prototype with what it changed against the brief; and one beat's issues — stubs, tickets, labels, comments, a PR — with two variants, a ticket whose spec does not hold and a spec session that was closed. Stages 1, 2, 3, 5, 6, 7 and 8 each run twice, once against each inventory, so every stage is checked both for naming its skills and for giving the fallback when they are absent. Stage 0 checks the collision path into `ADOPTING.md`; stage 4 that the gate scopes its grill and leaves go or no-go to the human. Three more cover the boundaries the pipeline exists for: a fresh session resumes a beat from its issues alone and names its stage; a ticket session that finds its spec wrong flags on the beat's issue, sets `ticket:blocked`, and stops; and traditional-SDLC work is named as a separate pipeline. Every eval asserts that the session names its stage and where its authority ends. Run by hand with `skill-creator` before a merge that changes `SKILL.md`, and record the outcome in the pull request.
